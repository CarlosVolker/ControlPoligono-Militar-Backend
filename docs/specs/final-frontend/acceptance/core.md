# Criterios de aceptación — Núcleo de cliente (AC-CORE)

> 📖 Volumen del conjunto de aceptación `acceptance/` (método y convenciones en este archivo; matrices de cobertura en [`coverage.md`](coverage.md); estado, gates y autorizaciones en [`../verification.md`](../verification.md)). Estado global: **NO EJECUTADO** — ningún criterio de este archivo se ha comprobado sobre el producto ni se da por cumplido; ninguno afirma runtime del backend. Estos cinco criterios son transversales: rigen para las 36 pantallas y los 99 flujos, y se comprueban **en los mismos escenarios** que los `AC-OP-*`/`AC-FL-*` citados en cada fila, nunca en abstracto. Cada `AC-CORE-*` tiene su equivalente de implementación en el stream de tareas (`T-CORE-*` de `tasks.md`, mantenido por su propio writer; el cruce lo hace el integrador): la tarea implementa, el AC observa.

## Método (M-D / M-U) y convenciones del corpus `acceptance/`

| Método | Definición | Peso |
|---|---|---|
| **M-U — comprobación de usuario** | El operador autorizado ejecuta la acción sobre la pantalla real, contra el backend real y con datos reales, y compara el resultado con el criterio. Cada punto requiere autorización explícita y por separado ([`../verification.md`](../verification.md), «Requisito de autorización»). **Ninguna M-U se ha ejecutado hasta la fecha.** | **La única que decide** si el objetivo se cumplió |
| **M-D — comprobación documental** | Contraste estático spec ↔ código del cliente ↔ catálogos durables sin ejecutar nada (inspección de archivos, conteo de IDs contra el manifiesto, presencia/ausencia de patrones). | Apoya; **no sustituye** a M-U. Tests, build, lint y typecheck tampoco son prueba de usuario, y su uso futuro exige autorización específica (qué suite y qué AC apoya), no un «ejecutar todo y que pase» |

**Convenciones de columnas (volúmenes de familia).** `Método + ruta` = operación HTTP explícita con prefijo `/api/` (`PUT` y `PATCH` son criterios separados; ninguna fila abrevia un rango CRUD). `Precondición` = contexto y datos reales; si el dato necesario no existe, el criterio queda pendiente por falta de dato real — fixtures, mocks y registros sintéticos están prohibidos, y los ejemplos usan sólo placeholders genéricos (sin PII). `Acción` = pantalla y flujo canónicos (`SCREEN-*`, `FL-*`). `Observable` = resultado de usuario con la respuesta citada desde el contrato durable y el refresco de relaciones. `Fallo/vacío/denied/cancelación` = deltas sobre las clases `F-01…F-12` y los estados `ST-*` del perfil `P-*` de la OP. `DS` = página de referencia de la biblioteca externa.

**Estado y prohibiciones.** Todo AC de este corpus está `NOT_VERIFIED` (ninguna comprobación de usuario ejecutada); ninguno se da por cumplido y ningún gate está `passed`. No se afirma runtime del backend; no se simulan capacidades sin endpoint (D-02); los V-* anteriores se retienen mediante la tabla de equivalencias de [`coverage.md`](coverage.md).

**Autoridad de stack (orden del operador, 2026-10-02).** Vue 3 Composition API con `<script setup lang="ts">` + **TypeScript** (deroga el mandato JavaScript anterior), Pinia, Vue Router (`createWebHistory`), CSS vanilla, Inume Design System 1:1. El código actual del cliente **está en TypeScript** (38 `.vue` con `lang="ts"`, 34 `.ts`, 0 `.js`; verificado 2026-10-15): el baseline JavaScript es hecho histórico, superado (`../experience/screens.md` §Convenciones, `../experience/navigation.md` cabecera, `../design-system/visual-contract.md` §Traslado).
